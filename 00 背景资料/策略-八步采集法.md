# 策略-八步采集法

> 政策采集 SOP。建设期人工 + Claude 辅助执行;维护期由 `policy-watch` skill 自动跑。
> 服务对象:滴滴能源决策层(参见 [[滴滴能源-政策分析背景]])
> 依赖基建:[[渠道目录]] · [[政策重要性打分体系]]

---

## 一句话总览

**遍历渠道抓增量 → 标题过滤 + 去重 → 抓正文 + 六维打分 → 入库 → 按分找评论 → 反扫优质公众号 → 找缺口 → 反哺渠道目录**

闭环的关键在 Step 7-8:通过优质公众号的历史引用反推采集盲区,把"不知道自己不知道"的政策补进来。

---

## 工具分工

| 工具 | 主要职责 | 依据 |
|------|---------|------|
| **Tavily** | Step 2 搜索发现、Step 6 评论搜索、Type A 补抓的 URL 发现 | AI 语义排序,`include_domains` 过滤好用,媒体/社区覆盖广 |
| **Firecrawl** | Step 4 正文抓取(政府/媒体网页、PDF) — **首选** | Markdown 转换质量高,`--only-main-content` 去噪,PDF 解析强 |
| **Python `requests` + `trafilatura`** | Step 4 / Step 6 抓取的**兜底替代**(Firecrawl 额度耗尽时) | 完全免费,gov.cn 抓取成功率 ~95%,质量略低于 Firecrawl 但可接受 |
| **wechat-article-to-markdown** | Step 6/7 公众号单文章抓取 | 单 URL → Markdown + 图,懒加载修复 |
| **搜狗微信搜索**(`weixin.sogou.com`) | Step 7 公众号历史翻页 | 能枚举公众号历史,反爬偏重需节流(Python 直连即可,实测稳定) |
| **飞书订阅号** | Step 2 公众号增量发现(未来向) | 订阅后只推新发,不能拉历史 |
| **≥4 分政策交叉验证** | Tavily + Firecrawl 双抓对比 | 高价值内容冗余,取更完整版本 |

**环境前提**:Tavily / Firecrawl 为海外 API,本机需代理可达;`trafilatura` 走本地 Python,不依赖海外服务。

### Firecrawl 额度耗尽时的兜底降级路径(本轮已验证)

```
Step 4 抓取(政策正文):
  ┌─ Firecrawl 首选(质量高)
  └─ 失败/无额度 → Tavily search 找 URL → Python requests + trafilatura 提取
                     ↓
                  trafilatura 抽不到主内容 → BeautifulSoup 兜底全文清洗
                     ↓
                  仍失败 → 标 fetch_error,人工

Step 6 抓取(评论正文): 同上链路
```

**实测对比**(2026-04-25 第一轮 Type A 补抓):
- Firecrawl Step 4' / 4d:抓 273 篇 ok 253 / fail 20(成功率 92%)
- **Tavily+trafilatura Type A:抓 44 篇 ok 44 / fail 0(成功率 100%)**
- Tavily+trafilatura Step 6 typeA 评论:88 篇 ok / 5 fail(成功率 95%)

兜底链路不是质量妥协,实测更稳。Firecrawl 仍作首选(支持 PDF + JS 渲染),但 trafilatura 路径已是 SOP 的法定 plan B。

## Step 1 · 去重基线建立

**目的**:为后续 Step 3、Step 5 提供查重参照。解决 backup 里同政策多版本(带/不带文号、不同 UUID)的顽疾。

**输入**:`01 核心政策/` 现有文件(首次跑为空;维护期为增量前快照)

**动作**:
1. 扫描所有 `.md` 文件
2. 提取每文件的:
   - **文号**(frontmatter `文号` 字段 或 标题括号里的发改/能源/国办字号)
   - **标题规范化哈希**:去除括号/空格/标点后取 SHA-256 前 12 位
3. 构建索引 JSONL:
   ```json
   {"文号": "发改能源〔2024〕718号", "标题哈希": "a3f5c8...", "路径": "01 核心政策/xxx.md"}
   ```
4. 写入 `00 背景资料/collection-meta/baseline-YYYYMMDD.jsonl`

**异常**:
- 无文号(如指导意见)→ 仅用标题哈希作键
- 同文号多文件 → 记入"需人工消歧"清单

**产出**:`baseline-YYYYMMDD.jsonl`

## Step 2 · 按渠道增量扫描(遍历至边际效益收敛)

**目的**:从渠道目录拉候选政策。建设期力求尽可能遍历,不再取固定 TOP N。

### 渠道范围(本次正式扩展)

| 层级 | 目标覆盖 | 当前 | 策略 |
|------|---------|------|------|
| 国家级 | 13(已覆盖) | ✅ | 继续维护 |
| 省级 | **31 全覆盖** | ~6 | 模板化批量补 |
| 地市级 | **~330 全覆盖** | ~10 | 模板化 + 业务驱动优先 |
| **直辖市下辖区** | **京沪津渝 ~80 区全覆盖** | 0 | 直辖市作市级处理,下辖区作"市级子区"专项扫描 |
| 一般地级市下辖区/县 | **本轮不做** | ~0 | 放一边,未来按需 |

**扩展四策**:
1. **业务驱动**:滴滴充电场站覆盖的前 30 城市优先补齐
2. **反哺驱动**:Step 8 缺口分析里真的出现过该渠道才补
3. **模板化**:建"省/市 → 发改委 / 能源局 / 住建厅 / 政府网"四字段模板
4. **直辖市区级专项**:京沪津渝下辖区独立查询,关键词带"区+市名"组合,自动标 `is_district: true`

### 搜索执行

**工具**:**Tavily**(主) — AI 语义排序,`include_domains` 过滤渠道目录根域名。

**关键词**:渠道目录 4 条主线 + 标题识别规则特征词。

**遍历策略**(每个 `渠道 × 关键词` 组合):翻页直到命中任一停止条件(OR):

```
[边际效益]  连续 3 页"新政策/总结果"比例 < 10%
[时间尾部]  搜索结果时间戳跌出回溯窗口(建设期 3 年 / 维护期 24h)
[硬上限]    已翻 20 页(兜底,防死循环)
[配额]      当日 API 配额剩余 < 10%(留给其他组合)
```

**语义去重**:对候选标题做简化(去括号/空格/标点/机构名)后算 Jaccard 相似度,> 0.85 视为同政策,只保留时间最早者。避免"充电桩政策"与"充换电设施政策"两组搜索抓到同一篇,加速边际收敛。

### 公众号增量发现(并行子线)

**工具**:**飞书订阅号**(能力 = 只推新发,不拉历史)。

作用:跟渠道目录的"根域名"扫描并行,捕捉公众号**未来**新发政策(Step 7 才做历史反扫)。

订阅清单来自 Step 7 的"优质号白名单"(首次运行为空,逐轮滚入)。

**产出**:`candidates-YYYYMMDD.jsonl`(含 title / url / source_domain / date / source_type)

### Step 2.5 · 渠道发现回写(每次 Step 2 后立即跑)

**目的**:把 Step 2 抓到的 URL 里**渠道目录尚未收录的根域名**,实时回写到 `渠道目录.md` 的"discovered 待提升"段。避免"看见了但要等 Step 8 才整理"的拖延。

**动作**:
1. 扫 `candidates*.jsonl` 的 `source_domain` 字段
2. 对照 `渠道目录.md` 现有 + 候选段,找出新出现的根域名
3. 计算每个新域名的命中数(出现在多少政策候选里)
4. 追加到 `渠道目录.md` 末尾的 **"## 自动发现段(待人工提升)"** 段:
   ```
   | 根域名 | 首次发现 | 命中政策数 | 状态 |
   |--------|---------|-----------|:----:|
   | xxx.gov.cn | 2026-04-25 | 5 | 待提升 |
   ```
5. 同步写日志 `00 背景资料/collection-meta/YYYY-MM-DD/discovered-channels.jsonl`

**提升规则**:
- 命中数 ≥3 且首次发现 ≥7 天前 → Step 8 时人工 review,通过后移到正式段
- 命中数 1-2 → 留在自动发现段观察
- 命中数 ≥3 但来源不是 .gov.cn / 行业媒体 → 标 `suspect`,人工判断

**这个机制让渠道目录从"周/月级回写"升级到"每日同步",维护期 cron 跑完 Step 2 就更新一次,不积压**。

## Step 3 · 标题规则过滤 + 查重

**目的**:过噪声 + 已入库项。

**输入**:Step 2 候选清单 + Step 1 基线索引

**动作**:
1. **标题识别规则**(渠道目录已定义):
   - 含政策特征词:关于 / 指导意见 / 通知 / 行动方案 / 管理办法 / 工作方案 / 技术标准
   - 带年份 + 发布机构
   - 不含情绪/新闻词
2. **时间校验**:发布日期在窗口内
3. **查重**:标题规范化哈希 vs Step 1 基线 → 已存在丢弃
4. **文号查重**(若可提取):避免"同政策不同标题"漏网

**产出**:`filtered-candidates-YYYYMMDD.jsonl`(过滤后,通常剩 30-50%)

## Step 3.5 · URL 维度查重(2026-04-26 新增)

**目的**:补 Step 3 漏掉的 URL 维度,防止"同 URL 重复抓取入库"。

**为何必须**:实证发现 71 / 357 ≈ **20% 政策是同 URL 重复入库**(L1 多次跑同一渠道时,同政策 URL 被反复抓回入库,而 Step 3 的"标题哈希"+"文号"查重会因抓取版本差异(PDF vs HTML / 不同采集时点)漏过)。Step 3.5 用 URL 作权威 fingerprint,是查重最可靠的一道闸。

**输入**:Step 3 输出 + 现有 vault `0_raw/policies/` + `0_raw/_duplicates/`(已识别 dup,作为强基线)

**动作**:
1. **构建三维基线**(扫描 `0_raw/policies/` + `0_raw/_duplicates/` 全部 frontmatter):
   - URL fingerprint(去 query/fragment/末尾斜杠)
   - 标题规范化哈希
   - 文号归一化(去机构前缀,如"生态环境部令第19号" → "部令第19号")
2. **逐候选比对**(任一维度命中即视为已入库,优先级 URL > 文号 > 标题):
   - URL 命中 → 必丢(可信度最高,采集失败可重试时也走此 dim)
   - 文号命中 → 丢(同政策不同采集源)
   - 标题哈希命中 → 丢(同政策不同表述)
3. **输出**:
   - `deduped-r2.jsonl`:去重后,真增量
   - `rejected-as-dup.jsonl`:被识别 dup 的(含 `_dup_dim` / `_matched_files`)

**实施脚本**:`~/.openclaw/skills/policy-watch/scripts/step3_5_url_dedup.py`

```bash
python3 step3_5_url_dedup.py \
  --candidates filtered-r2.jsonl \
  --out deduped-r2.jsonl \
  --rejected rejected-dup.jsonl
```

也可独立扫现状(`--scan-only`)输出 baseline 索引数。

**与 v1 dedup 的区别**:`_meta/scripts/dedup_policies.py`(v1+v2)是**事后 dedup**(0_raw 已重复后清理);Step 3.5 是**事前查重**(L1 入库前拦截),理论上可以让事后 dedup 永远空跑。

**异常**:
- candidate 完全无 URL/文号/标题(残缺数据)→ 标 `incomplete`,人工审
- URL 命中但内容版本明显新于 baseline(如新公告替代 PDF)→ Step 3.5 仍丢,但 lint 提醒"已有此 URL,可能错过新版本"

## Step 4 · 抓取正文到暂存区(分层方案)

**目的**:按源类型分层抓取,暂存不入主库。

### 分层抓取

| 源类型 | 工具 | 方法 | confidence 基线 |
|--------|------|------|----------------|
| **A 政府官网** (ndrc / nea / mee / mof / 各地政府 gov.cn) | Firecrawl | `--only-main-content` + PDF 解析 | 0.95 |
| **B 行业媒体/转载** (北极星、21财经、中国能源网等) | Firecrawl | `--only-main-content` | 0.70 |
| **C 微信公众号** (mp.weixin.qq.com) | `wechat-article-to-markdown` 脚本 | 单 URL → md + 图 | 0.70-0.90(看号权威度) |
| **D PDF 附件** (政策原件 PDF 链接) | Firecrawl PDF 模式 | 失败兜底 `pdftotext` | 0.95 |

**交叉验证**:Step 2 标记为"重要候选"(搜索排名 TOP 3 或来自权威渠道)的政策,同时用 Tavily + Firecrawl 抓两次,取文本更完整的版本。

### 统一出口

所有抓取都写到:
```
00 背景资料/collection-meta/staging/YYYYMMDD/<hash>/
├── content.md       抓取后的 markdown
├── source.html      原始 HTML(备份用)
├── images/          (仅公众号有)
└── meta.json        { url, source_type, fetched_at, tool_used, confidence }
```

入库时 staging → `01 核心政策/`(Step 5 完成)。

**异常**:
- 抓取失败 → 记入失败清单,Step 8 前人工补抓
- 同 URL 多工具结果差异 > 20%(按字符数)→ 标"内容分歧"待人工

## Step 4.5 · 结构化抽取(正则 + LLM 级联)

**目的**:把 Step 4 抓到的 markdown 正文转成结构化字段,喂给 Step 5 打分。解决原 skill "纯脚本正则抽取,模型不够好"的问题。

### 抽取策略:混合级联

| 字段 | 强正则 | LLM 兜底 | 说明 |
|------|:-----:|:------:|------|
| 文号 | ✅ 主 | ✅ 兜底 | 正则 `[发改\|能源\|工信\|商务\|国办\|两办].*?〔\d{4}〕\d+号`;失败丢 LLM |
| 发布日期 | ✅ 主 | ✅ 兜底 | `\d{4}年\d{1,2}月\d{1,2}日` / `\d{4}-\d{1,2}-\d{1,2}` |
| URL → 渠道 | ✅ | — | 查 [[渠道目录]] 根域名映射 |
| 政策核心标题(去"关于印发""的通知"前后缀) | 部分 | ✅ | LLM 对 H1 做精简,保留主语 |
| 发文机构全名 | 部分(URL 映射) | ✅ | LLM 从正文开头抽完整名 |
| 正文主体边界(切"附件/相关链接/解读") | 启发式 | ✅ | LLM 判断正文终止点 |
| 业务标签(多选:V2G / 储能 / 充电 / 加油 / 电力市场 / ...) | 关键词粗筛 | ✅ 精判 | 正则先过,LLM 去噪 |
| 2-3 句摘要 | — | ✅ 必须 | 给 Step 5 打分和 Step 6 决策层简报用 |
| 初步影响分析(D1/D2 参考) | — | ✅ 必须 | 分业务三段:加油/充电/电力 |

### 级联规则

```
for each 字段:
  try 正则抽
  if 抽到 and 置信度高: 记 regex_hit
  elif 抽到 but 值可疑(如日期超窗、文号格式异常): 调 LLM 验证
  elif 未抽到: 调 LLM
  记入 extraction.jsonl:
    {field, method: regex_hit|llm_fallback|failed, value, confidence}
```

### LLM 调用(Claude Opus 4.7,本机已在)

单次调用抽多字段,批量节省 token。Prompt 骨架:

```
你是政策文本结构化抽取助手。输入是一篇政策全文 markdown,请输出 JSON:

{
  "核心标题": "...",       # 去除"关于""的通知"前后缀的政策主体名
  "发文机构": "...",       # 完整正式名(如"国家发展改革委")
  "文号": "...",          # 若正文有,否则 null
  "发布日期": "YYYY-MM-DD",
  "正文结束位置": "...",    # 正文最后一段的前 20 字(用于切附件)
  "业务标签": ["V2G", ...], # 多选: V2G/储能/充电/加油/综合能源/电力市场/碳排放/设备更新/新能源汽车/氢能
  "摘要": "...",          # 2-3 句
  "影响分析": {
    "加油业务": "...",     # 1 句,或 "无影响"
    "充电业务": "...",
    "电力业务": "..."
  }
}

只输出 JSON,不要解释。
```

### 质量门

| 情况 | 处理 |
|------|------|
| 必填字段(title / url / date)缺一 | 标 `fetch_error`,入人工清单 |
| 正则文号 + LLM 文号 **一致** | `confidence: 0.95` |
| 正则文号 + LLM 文号 **分歧** | `confidence: 0.80`,两版本都存,待人工 |
| 正则抽到 + LLM 未抽到(或相反) | `confidence: 0.85` |
| LLM 返回非 JSON | 重试 1 次;再失败标 `extraction_error` 人工 |

### 产出

- `collection-meta/staging/YYYYMMDD/<hash>/extracted.json`(每篇政策结构化字段)
- `collection-meta/YYYY-MM-DD/extraction.jsonl`(抽取日志,每字段 regex_hit / llm_fallback / failed 比例)

### 建设期调参计划

前 10 篇先跑,记录每字段:
- 正则命中率
- LLM 兜底率
- 失败率

跑完调整:
- 命中率 >95% 的字段:正则固化,不再调 LLM
- 命中率 <50% 的字段:拆 LLM prompt 或 加正则变体
- 失败率 >10% 的字段:报告里标黄,下轮优化

## Step 5 · 六维打分 + 入库

**目的**:按 [[政策重要性打分体系]] 打分,过阈值正式入库。

**动作**:
1. 对 staging 里每篇正文,Claude 按六维打分:
   - D1 业务关联度(0-5,权重 40%)
   - D2 直接影响度(0-5,权重 40%)
   - D3 发布主体层级(0-5,权重 20%)
   - D4 紧迫性(0-5,独立,用于行动分类)
   - D5 实操性(0-5,独立)
   - D6 机会窗口(0-5,独立)
2. 综合分 = `round(D1×0.4 + D2×0.4 + D3×0.2)`
3. 行动分类(A 立即 / B 研究 / C 跟进 / D 跟踪),D6 机会窗口 5-4 前跳一档,2-1 降一档
4. 价值标签(🛡️合规 / 🚀机会 / ⚔️壁垒 / 🔭趋势,可多选)
5. **阈值处理**(全部入库,阈值只控后续动作):
   - 全部综合分 → 入库 `01 核心政策/`(包括 1-2 分,作大盘存档)
   - 综合分 ≥3 → 触发 Step 6 抓评论
   - 综合分 ≥4 → 推送决策层频道(维护期)
   - 综合分 <3 → 入库后**不抓评论 / 不推送**,frontmatter 加 `archive: low_score`
6. **命名**:`【政策全称(文号)】-发文机构-UUID4.md`(UUID4 = 标题哈希前 4 位)
7. **frontmatter 必填**:
   ```yaml
   ---
   title: 完整政策标题
   source: 发文机构
   文号: 发改能源〔2024〕718号
   date: 2024-01-05
   url: 原始 URL
   source_type: A  # A=政府/B=媒体/C=公众号/D=PDF
   type: 核心政策
   重要性: 4
   行动分类: A
   价值标签: [合规, 机会]
   scores:
     D1: 5
     D2: 4
     D3: 4
     D4: 4
     D5: 4
     D6: 5
   confidence: 0.95
   tags:
     - 充电基础设施
     - V2G
   related: []
   ---
   ```

**异常**:
- 多次打分不一致 → 取中位数 + 记争议标记
- 同文号但标题有微差 → 用文号作主键,新入库覆盖旧

**产出**:`01 核心政策/` 新增 .md 文件 + 打分日志

---

## Step 6 · 按分找评论(阈值细化)

**目的**:为入库政策找对应密度的评论/解读,落 `02 政策评论/`。

### 按分配额

| 综合分 | 入库(Step 5) | 评论篇数(Step 6) | 来源组合要求 |
|:-----:|:----------:|:---------------:|-------------|
| 5 | ✅ | 3 篇 | 优质公众号 ≥1 + 官方媒体 ≥1 |
| 4 | ✅ | 3 篇 | 至少含 1 篇优质公众号 |
| 3 | ✅ | 1 篇 | 来源不限,优先权威 |
| <3 | ✅ 存档 | 0 篇 | 政策仍在库(`archive: low_score`),只是不抓评论也不推送 |

### 搜索工具

**主:Tavily** — 用政策名 + "解读" / "评论" / "分析" 搜,`include_domains` 优先 `mp.weixin.qq.com` + 行业媒体。

**备:Firecrawl** — Tavily 返回结果不足时补搜。

### 评论入库

- 公众号文章:`wechat-article-to-markdown` 脚本 → `02 政策评论/`
- 其他媒体:Firecrawl → `02 政策评论/`

**命名**:`<评论标题>-<来源公众号或媒体名>.md`

**评论自身 confidence**:
- 权威号(政府/部委直属媒体/头部政策号):0.9
- 行业媒体(21财经、北极星等):0.7
- 匿名博客/小号:0.5

**反链**:政策文件 `related` 字段追加;评论文件 frontmatter 加 `related_policy: [[政策文件名]]`。

**产出**:`02 政策评论/` 新增 + 双向反链

---

## Step 7 · 优质公众号反向扫描

**目的**:通过优质源的历史引用反推漏抓政策。

### 优质号识别

输入:Step 6 里出现过的所有公众号,统计:
- 出现 ≥3 次
- 引用政策置信度均值 ≥0.85
- 或人工白名单(少量专家账号直接标记)

### 历史反扫方法(B 主 + C 兜底)

**方案 B:搜狗微信搜索**(主力)
- `https://weixin.sogou.com/weixin?type=1&s_from=input&query=<公众号名>`
- 翻页抓该号近 12 月文章列表
- 对每篇文章用 `wechat-article-to-markdown` 抓正文
- **反爬响应处理**:返回 5xx / 验证码 / 频控 → 暂停该号、切 C、当日不再重试

**方案 C:人工兜底**
- B 失败 或 B 触发反爬后,将该号加入"人工待处理"清单
- 半月一次人工收集该号历史 URL 列表
- 逐 URL 丢给 `wechat-article-to-markdown`

**注**:飞书订阅号(原方案 A)已剥离到 Step 2 "公众号增量发现",**不参与** Step 7 历史反扫(因其不能拉历史)。

### 引用抽取

- 从每篇文章正文中提取"被引政策":
  - 正则匹配政策文号(如"发改能源〔2024〕xxx号"模式)
  - Claude 辅助抽取标题中的政策指代
- 汇总 → 历史引用清单

**产出**:`优质源-历史引用-YYYYMMDD.jsonl`(公众号 → 引用政策列表 + 来源文章 URL)

---

## Step 8 · 缺口分析 + 反哺渠道目录

**目的**:找出"漏了但圈内都在讨论"的政策,并修补采集源。

**动作**:
1. **对照**:Step 7 历史引用清单 vs Step 1 基线 + Step 5 新入库
2. **缺口分类**:
   - **Type A 政策遗漏**:政策存在但未收 → 直接回 Step 4 补抓
   - **Type B 渠道缺失**:政策来自渠道目录没有的源 → 新根域名加入 [[渠道目录]],标"下轮优先"
   - **Type C 地方政策盲区**:缺口集中在某省/市 → 省市级模板化批量补
3. **更新**:
   - `渠道目录.md` 追加新根域名,附首次发现日期与引入理由
   - `collection-meta/gaps-YYYYMMDD.jsonl` 记完整缺口清单
4. **反馈环**:Type B 新渠道下轮 Step 2 优先级最高;Type A 立即补抓不等下轮

**产出**:
- `gaps-YYYYMMDD.jsonl`
- 更新后的 `渠道目录.md`(frontmatter 加 `last_updated: YYYYMMDD`)

| 阶段 | 时长 | 产出 |
|------|------|------|
| Step 1-3 | 1-2 小时 | 基线 + 候选清单 |

|------|------|---------|

## 与 Karpathy LLM Wiki v2 的对接

本 SOP 是 L1 采集层;入库后的文件由 L2(LLM Wiki)skill 继续加工:
- Step 5 的 frontmatter 已满足 v2 的 `confidence` / `provenance`(url+source_type)/ `type`
- Step 6 的 related 反链满足 v2 的双向链接
- L2 skill 会继续补:`supersedes` / `iterates` / `impacts` 等强类型关系(扫正文自动推断)

## 常见异常与应对

| 情况 | 应对 |
|------|------|
| Tavily / Firecrawl 超限 | 跑到哪断到哪,写断点 JSON,下轮 resume |
| 正文明显是摘要而非原文 | 标 `confidence: 0.6`,Step 5 降档 |
| 一个政策多渠道首发 | 取发布日期最早者为主,其他作 `sources` 数组存 |
| 打分争议大(2 次差 ≥2) | 落人工审核清单,暂不入库 |
| 搜狗微信反爬触发 | 暂停该号采集,切 C 人工兜底 |
| PDF 解析失败 | `pdftotext` 兜底;仍失败则标 `fetch_error` 人工处理 |
