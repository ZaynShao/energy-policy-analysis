## L1 数据原则(2026-04-29 新增,SOP 基线)

本项目奉行 **Raw immutable + 派生分层** 原则(详见项目根 [[CLAUDE]] §LLM Wiki 设计原则)。`0_raw/policies/` 是 **L1 raw source 层**,落到八步采集法的具体约束:

1. **Raw 一旦入库,任何后续流程禁止修改其内容**。Step 5A 之后,L2 关系抽取 / L3 月报渲染 / 评分迭代 / 搜索系统 / 反链回写 — 任一流程都不得改写 `0_raw/policies/*.md` 的 frontmatter 业务字段或 body 段落。发现 raw 不准确 → 重抓重入,不就地编辑(命名后缀 `_v2` 区分,旧版迁 `_archive/`)
2. **派生分层**:任何对 raw 的解读、评分、业务关联判断、跨政策对比 — 这些都属派生层(L2),必须落到 `_meta/business_view/{pid}.yaml` 或 `1_extracted/` 子目录,**不进 L1 文件**
3. **Append-only**:派生错了 → 重抽派生层、覆盖派生文件;**不是回头去改 raw**。raw 是不变的事实层,派生是可变的解读层
4. **可追溯**:每个派生字段必须能指回 raw 源(`_meta/business_view/{pid}.yaml` 的 `sanitized_from` / `1_extracted/relations/*.jsonl` 的 `pid` 字段都已遵循)
5. **L1 frontmatter 白名单**(只允许这些字段,见 Step 5):
   `id / aliases / title / official_number / issuer / date / region / provenance / type / confidence / issuer_canonical / dup_aliases / dedup_at / dedup_rule / subtype / _duplicate_of / _duplicate_reason`
   — 任何超出此白名单的字段(尤其评分类、判断类、业务标签类、关系类)出现在 L1 frontmatter 即视为污染
   - 注:`tags` / `重要性` / `行动分类` / `价值标签` / `scores` / `related` 都已下沉到派生层(2026-04-29 解耦),不再允许出现在 L1 frontmatter
6. **L1 body 内容范围**:**只允许** `## 政策原文`(及其 ### 子段,只能是政策原文条款字面)。
   - **禁止段**:`## 摘要`(LLM 生成,2026-04-29 起下沉 5C `business_view.summary`)、`## 初步影响分析`、`## 六维评分`、`## 业务关联`、`## 跟进建议`、`## 战略地位映射` — 全部业务派生段

**verify**:
```bash
# L1 frontmatter 白名单审计
python3 _meta/scripts/lint_l1_frontmatter.py   # 待建,扫非白名单字段
# L1 body 段审计(应为 0)
grep -lir "## 摘要\|## 初步影响分析\|## 六维评分\|## 业务关联\|## 跟进建议\|战略地位映射" 0_raw/policies/ | wc -l
```

历史污染由 L1.2 一次性净化清理(2026-04-29 已跑 247 篇删 ## 初步影响分析 + ## 六维评分;补丁 L1.2.b 跑 263 篇删 ## 摘要)。SOP 此后入库的政策按 Step 5 白名单 + 5C 异步派生执行,不再产生此类污染。

> 这条原则看似把分析能力从 L1 剥离,实际上**是把分析能力从 L1 移到 L2** — 派生层可以反复重抽、迭代、重新评分,而 L1 raw 提供稳定的事实底座。Karpathy LLM Wiki 思路的核心:raw 提供 trust,派生提供 insight,二者不能混。

## 工具分工

| 工具 | 主要职责 | 依据 |
|------|---------|------|
| **Tavily** | Step 2 政策搜索发现、Type A 补抓的 URL 发现、Step 6 评论 pull 兜底 | AI 语义排序,`include_domains` 过滤好用,媒体/社区覆盖广 |
| **Firecrawl** | Step 4 政策正文抓取(政府/媒体网页、PDF) — **首选** | Markdown 转换质量高,`--only-main-content` 去噪,PDF 解析强 |
| **Python `requests` + `trafilatura`** | Step 4 抓取的**兜底替代**(Firecrawl 额度耗尽时) | 完全免费,gov.cn 抓取成功率 ~95%,质量略低于 Firecrawl 但可接受 |
| **wewe-rss**(本地 `localhost:4000`)| **Step 2/6 评论 push 主路径** + Step 7 优质号订阅扩容(替代旧搜狗历史反扫)| 微信读书内置 RSS,后台 SQLite 预拉全文,0 次微信 API 调用,反爬风险 0,订阅后全量历史可见 |
| **wechat-article-to-markdown** | Step 6 评论 pull 兜底单文章抓取(Tavily 命中后) | 单 URL → Markdown + 图,懒加载修复 |
| **Claude Opus 4.7**(本机已在)| Step 4.5 客观元数据抽取、Step 5C 业务侧派生、Step 6.5 B3 LLM 精判 | 派生层主力 |
| **≥4 分政策交叉验证** | Tavily + Firecrawl 双抓对比 | 高价值内容冗余,取更完整版本 |
| **飞书订阅号** | (备选)wewe-rss 不可达号的 fallback 通知机制 | 订阅后只推新发,无内容存储,2026-04-29 实操不依赖 |
| **搜狗微信搜索** | ❌ 已废弃 — wewe-rss 替代 | 反爬高,历史覆盖不全,旧 Step 7 已重写 |

**环境前提**:Tavily / Firecrawl 为海外 API,本机需代理可达;`trafilatura` 走本地 Python,不依赖海外服务。

### Firecrawl 额度耗尽时的兜底降级路径(本轮已验证)

```
Step 4 抓取(政策正文):
  ┌─ Firecrawl 首选(质量高)
  └─ 失败/无额度 → Tavily search 找 URL → Python requests + trafilatura 提取
                     ↓
                  trafilatura 抽不到主内容 → BeautifulSoup 兜底全文清洗
                     ↓
                  仍失败 → 标 fetch_error,人工

Step 6 抓取(评论正文): 同上链路
```

**实测对比**(2026-04-25 第一轮 Type A 补抓):
- Firecrawl Step 4' / 4d:抓 273 篇 ok 253 / fail 20(成功率 92%)
- **Tavily+trafilatura Type A:抓 44 篇 ok 44 / fail 0(成功率 100%)**
- Tavily+trafilatura Step 6 typeA 评论:88 篇 ok / 5 fail(成功率 95%)

兜底链路不是质量妥协,实测更稳。Firecrawl 仍作首选(支持 PDF + JS 渲染),但 trafilatura 路径已是 SOP 的法定 plan B。

## Step 1 · 去重基线建立

**目的**:为后续 Step 3、Step 5 提供查重参照。解决 backup 里同政策多版本(带/不带文号、不同 UUID)的顽疾。

**输入**:`01 核心政策/` 现有文件(首次跑为空;维护期为增量前快照)

**动作**:
1. 扫描所有 `.md` 文件
2. 提取每文件的:
   - **文号**(frontmatter `文号` 字段 或 标题括号里的发改/能源/国办字号)
   - **标题规范化哈希**:去除括号/空格/标点后取 SHA-256 前 12 位
3. 构建索引 JSONL:
   ```json
   {"文号": "发改能源〔2024〕718号", "标题哈希": "a3f5c8...", "路径": "01 核心政策/xxx.md"}
   ```
4. 写入 `00 背景资料/collection-meta/baseline-YYYYMMDD.jsonl`

**异常**:
- 无文号(如指导意见)→ 仅用标题哈希作键
- 同文号多文件 → 记入"需人工消歧"清单

**产出**:`baseline-YYYYMMDD.jsonl`

## Step 2 · 按渠道增量扫描(遍历至边际效益收敛)

**目的**:从渠道目录拉候选政策。建设期力求尽可能遍历,不再取固定 TOP N。

### 渠道范围(本次正式扩展)

| 层级 | 目标覆盖 | 当前 | 策略 |
|------|---------|------|------|
| 国家级 | 13(已覆盖) | ✅ | 继续维护 |
| 省级 | **31 全覆盖** | ~6 | 模板化批量补 |
| 地市级 | **~330 全覆盖** | ~10 | 模板化 + 业务驱动优先 |
| **直辖市下辖区** | **京沪津渝 ~80 区全覆盖** | 0 | 直辖市作市级处理,下辖区作"市级子区"专项扫描 |
| 一般地级市下辖区/县 | **本轮不做** | ~0 | 放一边,未来按需 |

**扩展四策**:
1. **业务驱动**:滴滴充电场站覆盖的前 30 城市优先补齐
2. **反哺驱动**:Step 8 缺口分析里真的出现过该渠道才补
3. **模板化**:建"省/市 → 发改委 / 能源局 / 住建厅 / 政府网"四字段模板
4. **直辖市区级专项**:京沪津渝下辖区独立查询,关键词带"区+市名"组合,自动标 `is_district: true`

### 搜索执行

**工具**:**Tavily**(主) — AI 语义排序,`include_domains` 过滤渠道目录根域名。

**关键词**:渠道目录 4 条主线 + 标题识别规则特征词。

**遍历策略**(每个 `渠道 × 关键词` 组合):翻页直到命中任一停止条件(OR):

```
[边际效益]  连续 3 页"新政策/总结果"比例 < 10%
[时间尾部]  搜索结果时间戳跌出回溯窗口(建设期 3 年 / 维护期 24h)
[硬上限]    已翻 20 页(兜底,防死循环)
[配额]      当日 API 配额剩余 < 10%(留给其他组合)
```

**语义去重**:对候选标题做简化(去括号/空格/标点/机构名)后算 Jaccard 相似度,> 0.85 视为同政策,只保留时间最早者。避免"充电桩政策"与"充换电设施政策"两组搜索抓到同一篇,加速边际收敛。

### 公众号增量发现(并行子线)

**工具**:**wewe-rss**(微信读书 RSS 服务,本地 `http://localhost:4000`,后台 SQLite 预拉全文)。

作用:跟渠道目录的"根域名"扫描并行,持续 push 已订阅公众号的**新发文章**(评论 + 解读 + 偶有政策原文转载)。

订阅清单见 [[优质公众号白名单]](2026-04-29 现状:17+ 已实测涌现,1170 评论已采)。新优质号通过 Step 7 识别 + 人工加入 wewe-rss 订阅,push 链路立即生效。

**抓取脚本**:`_meta/scripts/wewe_rss_to_commentaries.py`(2026-04-29 主路径)
- 调 `/feeds/all.json` 拉 JSON Feed 1.1
- HTML → Markdown(复用 `wechat_article_pipeline.py`)
- URL 去重 + 标题噪音黑名单(会议/招聘/党建/喜报/招标/转发等)
- 入库 `0_raw/commentaries/{title}.md`,frontmatter 含 source_account / business_tag / commentary_type=待分类

**与原飞书订阅号方案的差异**:
- 飞书:只推新发,不拉历史 → wewe-rss:订阅后**全量历史 + 持续推**(原 Step 7 搜狗历史翻页因此被作废)
- 飞书:无内容存储,需另抓 → wewe-rss:本地 SQLite 已存全文 HTML,**0 次微信 API**就能入库
- 飞书:仍可作为 fallback 通知机制,但内容采集走 wewe-rss

**产出**:
- `candidates-YYYYMMDD.jsonl`(渠道目录的政策候选,主线)
- `0_raw/commentaries/*.md`(并行子线,RSS push 评论入库 — 关联到政策走 Step 6.5)

### Step 2.5 · 渠道发现回写(每次 Step 2 后立即跑)

**目的**:把 Step 2 抓到的 URL 里**渠道目录尚未收录的根域名**,实时回写到 `渠道目录.md` 的"discovered 待提升"段。避免"看见了但要等 Step 8 才整理"的拖延。

**动作**:
1. 扫 `candidates*.jsonl` 的 `source_domain` 字段
2. 对照 `渠道目录.md` 现有 + 候选段,找出新出现的根域名
3. 计算每个新域名的命中数(出现在多少政策候选里)
4. 追加到 `渠道目录.md` 末尾的 **"## 自动发现段(待人工提升)"** 段:
   ```
   | 根域名 | 首次发现 | 命中政策数 | 状态 |
   |--------|---------|-----------|:----:|
   | xxx.gov.cn | 2026-04-25 | 5 | 待提升 |
   ```
5. 同步写日志 `00 背景资料/collection-meta/YYYY-MM-DD/discovered-channels.jsonl`

**提升规则**:
- 命中数 ≥3 且首次发现 ≥7 天前 → Step 8 时人工 review,通过后移到正式段
- 命中数 1-2 → 留在自动发现段观察
- 命中数 ≥3 但来源不是 .gov.cn / 行业媒体 → 标 `suspect`,人工判断

**这个机制让渠道目录从"周/月级回写"升级到"每日同步",维护期 cron 跑完 Step 2 就更新一次,不积压**。

## Step 3.5 · URL 维度查重(2026-04-26 新增)

**目的**:补 Step 3 漏掉的 URL 维度,防止"同 URL 重复抓取入库"。

**为何必须**:实证发现 71 / 357 ≈ **20% 政策是同 URL 重复入库**(L1 多次跑同一渠道时,同政策 URL 被反复抓回入库,而 Step 3 的"标题哈希"+"文号"查重会因抓取版本差异(PDF vs HTML / 不同采集时点)漏过)。Step 3.5 用 URL 作权威 fingerprint,是查重最可靠的一道闸。

**输入**:Step 3 输出 + 现有 vault `0_raw/policies/` + `0_raw/_duplicates/`(已识别 dup,作为强基线)

**动作**:
1. **构建三维基线**(扫描 `0_raw/policies/` + `0_raw/_duplicates/` 全部 frontmatter):
   - URL fingerprint(去 query/fragment/末尾斜杠)
   - 标题规范化哈希
   - 文号归一化(去机构前缀,如"生态环境部令第19号" → "部令第19号")
2. **逐候选比对**(任一维度命中即视为已入库,优先级 URL > 文号 > 标题):
   - URL 命中 → 必丢(可信度最高,采集失败可重试时也走此 dim)
   - 文号命中 → 丢(同政策不同采集源)
   - 标题哈希命中 → 丢(同政策不同表述)
3. **输出**:
   - `deduped-r2.jsonl`:去重后,真增量
   - `rejected-as-dup.jsonl`:被识别 dup 的(含 `_dup_dim` / `_matched_files`)

**实施脚本**:`~/.openclaw/skills/policy-watch/scripts/step3_5_url_dedup.py`

```bash
python3 step3_5_url_dedup.py \
  --candidates filtered-r2.jsonl \
  --out deduped-r2.jsonl \
  --rejected rejected-dup.jsonl
```

也可独立扫现状(`--scan-only`)输出 baseline 索引数。

**与 v1 dedup 的区别**:`_meta/scripts/dedup_policies.py`(v1+v2)是**事后 dedup**(0_raw 已重复后清理);Step 3.5 是**事前查重**(L1 入库前拦截),理论上可以让事后 dedup 永远空跑。

**异常**:
- candidate 完全无 URL/文号/标题(残缺数据)→ 标 `incomplete`,人工审
- URL 命中但内容版本明显新于 baseline(如新公告替代 PDF)→ Step 3.5 仍丢,但 lint 提醒"已有此 URL,可能错过新版本"

## Step 4 · 抓取正文到暂存区(分层方案)

**目的**:按源类型分层抓取,暂存不入主库。

### 分层抓取

| 源类型 | 工具 | 方法 | confidence 基线 |
|--------|------|------|----------------|
| **A 政府官网** (ndrc / nea / mee / mof / 各地政府 gov.cn) | Firecrawl | `--only-main-content` + PDF 解析 | 0.95 |
| **B 行业媒体/转载** (北极星、21财经、中国能源网等) | Firecrawl | `--only-main-content` | 0.70 |
| **C 微信公众号** (mp.weixin.qq.com) | `wechat-article-to-markdown` 脚本 | 单 URL → md + 图 | 0.70-0.90(看号权威度) |
| **D PDF 附件** (政策原件 PDF 链接) | Firecrawl PDF 模式 | 失败兜底 `pdftotext` | 0.95 |
| **E 会议/讲话级信号**(国务院专题学习、领导讲话、能源局司长发言、国新办通气会、中央财经委会议) | Tavily search + Firecrawl/trafilatura | 政府新闻稿/官方通气稿/官方账号转载;**注明发言人 + 主持机构 + 日期** | 0.80(转述层有损耗) |

**交叉验证**:Step 2 标记为"重要候选"(搜索排名 TOP 3 或来自权威渠道)的政策,同时用 Tavily + Firecrawl 抓两次,取文本更完整的版本。

### 统一出口

所有抓取都写到:
```
00 背景资料/collection-meta/staging/YYYYMMDD/<hash>/
├── content.md       抓取后的 markdown
├── source.html      原始 HTML(备份用)
├── images/          (仅公众号有)
└── meta.json        { url, source_type, fetched_at, tool_used, confidence }
```

入库时 staging → `01 核心政策/`(Step 5 完成)。

**异常**:
- 抓取失败 → 记入失败清单,Step 8 前人工补抓
- 同 URL 多工具结果差异 > 20%(按字符数)→ 标"内容分歧"待人工

## Step 4.5 · 客观元数据抽取(只 raw 字段,不做派生)

**目的**:把 Step 4 抓到的 markdown 正文转成 **L1 raw 元数据**,供 Step 5 入库。**不做任何业务判断、语义分类、内容生成** — 这些下沉到 Step 5C 派生层。

**改造历史**:2026-04-29 前的 Step 4.5 抽「业务标签」「2-3 句摘要」(LLM 生成)并喂给 Step 5 打分,导致 LLM 派生字段污染 L1 raw。本版按 LLM Wiki Raw immutable 原则系统性解耦 — Step 4.5 只负责 deterministic 客观字段,所有 LLM 推断/生成统一在 Step 5C 做。

### 抽取字段(全部是 deterministic 客观字段)

| 字段 | 强正则 | LLM 兜底 | 说明 |
|------|:-----:|:------:|------|
| 文号 | ✅ 主 | ✅ 兜底 | 正则 `[发改\|能源\|工信\|商务\|国办\|两办].*?〔\d{4}〕\d+号`;失败丢 LLM |
| 发布日期 | ✅ 主 | ✅ 兜底 | `\d{4}年\d{1,2}月\d{1,2}日` / `\d{4}-\d{1,2}-\d{1,2}` |
| URL → 渠道 | ✅ | — | 查 [[渠道目录]] 根域名映射 |
| 政策核心标题(去"关于印发""的通知"前后缀) | 部分 | ✅ | LLM 对 H1 做**字面**精简,保留原文主语,不做语义改写 |
| 发文机构全名 | 部分(URL 映射) | ✅ | LLM 从正文开头抽**显式出现**的机构名,不做归类 |
| 正文主体边界(切"附件/相关链接/解读") | 启发式 | ✅ | LLM 判断正文终止点 |

**禁止字段**(原 Step 4.5 有,2026-04-29 删除,下沉 Step 5C):
- ❌ 业务标签(V2G/储能/充电...)— LLM 语义分类,属派生
- ❌ 2-3 句摘要 — LLM 生成内容,属派生
- ❌ 任何形式的 importance / score / category / tag — 都是派生

### 级联规则

```
for each 客观字段:
  try 正则抽
  if 抽到 and 置信度高: 记 regex_hit
  elif 抽到 but 值可疑(如日期超窗、文号格式异常): 调 LLM 验证(仅做字面提取确认,不语义判断)
  elif 未抽到: 调 LLM(仅做字面提取)
  记入 extraction.jsonl:
    {field, method: regex_hit|llm_fallback|failed, value, confidence}
```

### LLM 调用(Claude Opus 4.7,本机已在)

单次调用抽多字段,批量节省 token。Prompt 骨架:

```
你是政策文本元数据抽取助手。任务:从政策全文 markdown 里抽取**客观元数据字段**。
你不做任何业务判断、内容总结、语义分类、跨政策对比 — 那些是派生层 (Step 5C) 的事。

输入:政策全文 markdown
输出 JSON:

{
  "核心标题": "...",       # 字面提取 H1,去"关于""的通知"前后缀,不做语义改写
  "发文机构": "...",       # 字面提取正文开头机构名(如"国家发展改革委"),不做归一/分类
  "文号": "...",          # 正则文号字面(如"发改能源〔2024〕718号"),无则 null
  "发布日期": "YYYY-MM-DD", # 正文显式日期
  "正文结束位置": "..."     # 正文最后一段的前 20 字(用于切附件,只是定位标记)
}

只输出 JSON,不要解释。

**严禁字段**:摘要 / 业务标签 / 重要性 / 评分 / 影响分析 / 公司关联判断 — 这些都是派生,不在本 step 范围。如发现自己想写,直接 stop,只输出上述客观字段。
```

### 质量门

| 情况 | 处理 |
|------|------|
| 必填字段(title / url / date)缺一 | 标 `fetch_error`,入人工清单 |
| 正则文号 + LLM 文号 **一致** | `confidence: 0.95` |
| 正则文号 + LLM 文号 **分歧** | `confidence: 0.80`,两版本都存,待人工 |
| 正则抽到 + LLM 未抽到(或相反) | `confidence: 0.85` |
| LLM 返回非 JSON | 重试 1 次;再失败标 `extraction_error` 人工 |
| LLM 返回含禁止字段(摘要/业务标签等) | 重试 1 次,prompt 里强化禁止;再失败标 `extraction_error` 人工 |

### 产出

- `collection-meta/staging/YYYYMMDD/<hash>/extracted.json`(每篇政策客观元数据,**不含**摘要/业务标签等派生)
- `collection-meta/YYYY-MM-DD/extraction.jsonl`(抽取日志)

### 建设期调参计划

前 10 篇先跑,记录每字段:
- 正则命中率
- LLM 兜底率
- 失败率

跑完调整:
- 命中率 >95% 的字段:正则固化,不再调 LLM
- 命中率 <50% 的字段:拆 LLM prompt 或 加正则变体
- 失败率 >10% 的字段:报告里标黄,下轮优化

## Step 5C · 业务侧派生(异步,可缺失,独立写)

**目的**:在 L1 入库**之后**,独立跑 LLM 派生流程,产物按字段性质 **split 写到 3 处**(严格分层版,2026-04-29 A+ 重构):

| 字段 | 落地位置 | 性质 |
|---|---|---|

**关键属性**:
- **异步**:Step 5 入库完成立即可触发后续 step,不必等 5C
- **可缺失**:任一派生产物缺失 = "尚未派生",不阻塞 raw 操作

| LLM 派生时机 | Step 4.5 抽取时 + Step 5 打分时(混在 L1 入库流程里) | 独立 Step 5C(L1 入库后异步) |
| 派生失败影响 | 阻塞 L1 入库 | L1 已入库不受影响,business_view 缺失而已 |
| 派生迭代 | 改字段 → 263 篇 raw 全改一遍(实际发生) | 重跑 5C → business_view 全量覆盖,raw 不动 |
| 评论触发(Step 6)依赖 | 强依赖 L1 frontmatter `重要性` 字段 | 软依赖 business_view yaml,缺失则跳过抓评论 |

## Step 6 · 评论达成度评估 + 缺口补抓(RSS push 主 / Tavily pull 兜底)

**目的**:确保入库政策有**对应密度的关联评论**(达到「按分配额」目标),落 `0_raw/commentaries/`。

**核心范式转变**(2026-04-29 改造):
- 旧 SOP(pull-only):政策入库 → Tavily 主动搜该政策的评论 → 抓回入库
- 新 SOP(push 主 + pull 兜底):RSS push 已经持续涌入大量评论(Step 2 子线) → Step 6 评估"该政策的评论篇数是否够"→ 不够才用 Tavily 兜底补

### 触发条件(派生软依赖 5C)

- 必要前提:目标政策已通过 Step 5 入库 L1
- 软依赖:存在 `_meta/business_view/{pid}.yaml` 且综合分 ≥3
- 派生缺失处理:5C 尚未跑或 yaml 不存在 → 本 step **跳过该政策**(不阻塞,不报错),记入 `pending_step5c.jsonl` 等 5C 跑完后回扫
- **不允许**为了"让 Step 6 能跑"反向触发 5C 在 L1 入库流程里同步执行

### 按分配额(目标达成度)

| business_view 综合分 | 关联评论目标篇数 | 来源组合要求 |
|:-----:|:---------------:|-------------|
| 5 | 3 篇 | 优质公众号 ≥1 + 官方媒体 ≥1 |
| 4 | 3 篇 | 至少含 1 篇优质公众号 |
| 3 | 1 篇 | 来源不限,优先权威 |
| <3 | 0 篇 | business_view 标 `archive: low_score`,Step 6 跳过 |
| business_view 不存在 | 0 篇 | 跳过 + 记入 `pending_step5c.jsonl` |

### 评论获取路径(Push 主 / Pull 兜底)

**主路径 — wewe-rss push(已在 Step 2 子线持续运行)**:
- 17+ 优质公众号订阅持续涌入评论(详见 [[优质公众号白名单]])
- 已采评论池 `0_raw/commentaries/` 当前 1170 篇(2026-04-29)
- **关联**:由 Step 6.5 「评论→政策反向匹配」做(B1 文号匹配 + B2 标题模糊 + B3 LLM 精判)
- **达成度评估**:对每篇政策,扫 `0_raw/commentaries/*.md` frontmatter `related_policy: [[<政策>]]` 的反链数,与按分配额对比

**兜底路径 — Tavily pull(达成度不达标时启动)**:
- 触发条件:Step 6.5 跑完后,某政策仍未达"按分配额"目标
- 工具:Tavily 搜「<政策核心标题> 解读 OR 评论 OR 分析」,`include_domains` 优先 `mp.weixin.qq.com` + 行业媒体
- 抓取:命中评论 URL → `wechat-article-to-markdown`(单文章) / Firecrawl(其他媒体)→ `0_raw/commentaries/`
- 这部分等同于旧 SOP 的 Step 6 主路径,现在降级为补漏

**配额超额处理**:
- 优质号 push 经常某政策评论 > 3 篇,**全部入库不限量**(评论池越大,Step 7-8 反推渠道盲区越准)
- "按分配额"只是**达成度下限**,不是上限

### 评论入库 frontmatter(由 wewe_rss / Tavily 入口决定)

```yaml
---
title: "评论标题"
source_account: "<公众号名 或 媒体名>"
source_url: "..."
date_published: "YYYY-MM-DD"
fetched_at: "YYYY-MM-DDTHH:MM:SS+08:00"
commentary_type: 待分类      # 5.5C 评论侧派生跑后改:解读/分析/案例/数据/转发
business_tag: power           # power/charging/gas/cross
source: wewe-rss             # 或 tavily / firecrawl / wechat-article-to-markdown
confidence: 0.9              # 权威号 0.9 / 行业媒体 0.7 / 匿名 0.5
related_policy: ~            # Step 6.5 之后填,可多个 [[<政策>]]
related_policy_source: ~     # B1_official_number / B2_title_fuzzy / B3_llm / tavily_pull / manual
not_policy_related: ~        # Step 6.5 后置标:无政策可关联(化工/法律/海外行情)
---
```

**反链**:Step 6.5 跑完后,评论 frontmatter 的 `related_policy` 字段直接出现 wiki 链接 `[[<政策文件名>]]`。Obsidian 自动建反链;无需在政策 frontmatter 也写一遍(详见 §6.6 双向反链规范)。

**产出**:`0_raw/commentaries/` 持续增长 + Step 6.5 关联率监控指标

## Step 6.5 · 评论→政策反向匹配(2026-04-29 新增)

**目的**:把 RSS push 进来的评论反向关联到 vault 已有的政策。是 Step 6「按分配额达成度评估」的**前置**步骤(虽然命名在 6 后,但依赖上必须先跑)。

**为何独立成 step**:旧 SOP 假设 "评论是政策入库时反向 pull 的,关联在抓取时直接建立"。RSS push 范式下,评论先大规模入库,关联是后置的,需要独立流程匹配。

### 三路匹配级联(B1 → B2 → B3)

**B1 · 严格文号匹配**(高置信,~14 条/万评论):
- 输入:每篇评论正文
- 匹配:正则扫政策文号(如 `发改能源〔2024〕718号`),与 vault 政策 `official_number` 字段精确比对
- 命中 → 评论 frontmatter `related_policy: [[<政策>]]` + `related_policy_source: B1_official_number` + `confidence: 0.95`
- 工具:`/tmp/b1_match_official_number.py`(L3 session 已实现,需正式归档到 `_meta/scripts/`)

**B2 · 标题模糊匹配**(中置信,~130 条/万评论):
- 对 B1 未命中的评论,提取标题 8-gram,与 vault 政策标题做 Jaccard 相似度
- 阈值 ≥0.4 → 命中
- 命中 → `related_policy_source: B2_title_fuzzy` + `confidence: 0.75`
- **风险**:精度估计 70-85%,需 G4 抽样校验(参考 docs/handoffs/2026-04-29-link-system-followup-handoff.md)
- 工具:`/tmp/b2_match_title.py`(同上)

**B3 · LLM 4 路精判**(低召回但高质量,~6 条/万评论):
- 对 B1+B2 都未命中的评论,batch 丢给 4 路 LLM subagent 精判
- prompt:"这篇评论是否在讨论某条已入库政策?如是,指出 pid"
- 命中 → `related_policy_source: B3_llm` + `confidence: 0.85`
- **副产物**:LLM 精判过程会识别"无政策可关联"的评论(化工/法律/海外行情等),标 `not_policy_related: true` — 这些评论不再触发 Step 6 达成度计算
- 工具:`/tmp/b3_merge.py`(同上)

### 跑的频率

- 维护期 cron:每日凌晨跑一次,处理过去 24h push 进来的新评论
- 建设期手动:每周一次全量重跑(B1/B2 廉价可重跑;B3 LLM 调用贵,只对未匹配的跑)

### 监控指标(每次跑完输出)

```
关联率: linked / (total - not_policy_related) × 100%
       目前 (2026-04-29): 281 / (1170 - 0) = 24.0%
       目标 (G5 完成后): > 80%   (因 not_policy_related 标完后分母大幅缩小)

各路贡献:
  B1: +14
  B2: +130(精度待 G4 校验)
  B3: +6
  人工: +131(已存量)
```

### 输出

- 更新 `0_raw/commentaries/*.md` frontmatter `related_policy / related_policy_source / confidence / not_policy_related` 字段(**这是对 raw 的修改 — 但限于 frontmatter 关联类元数据,不动评论 body,符合 "raw 不可修改" 原则的边界例外:`related_policy` 是 vault 关系网的事实层之一**)
- 反链页 `1_extracted/relations/_index_by_policy/{pid}.md` 自动重生(由 `/tmp/rebuild_reverse_links_v2.py` 跑)
- 关联率日志 `_meta/scripts/log_step6_5_run_YYYYMMDD.json`

### Step 6.5 与 raw immutable 的关系澄清

`related_policy` 字段写到评论 frontmatter,看起来违反 "raw 一旦入库不可修改"。约定:
- **允许写 raw frontmatter 的字段(白名单)**:`related_policy / related_policy_source / not_policy_related` — 这些是 vault 内部关系网,不是 LLM 解读
- **禁止写 raw 的**:任何 LLM 生成内容(摘要/标签/影响分析等)— 这些走派生层 _meta/business_view/

详见 [[CLAUDE]] §LLM Wiki 设计原则 §2 的「关键判定」段。

## Step 7 · 优质公众号识别 + 订阅扩容(2026-04-29 重写)

**目的**:发现尚未订阅但应该订阅的优质公众号,加入 wewe-rss 订阅源,扩大评论池。

**范式转变**:
- 旧 SOP:用搜狗微信搜索翻页爬已识别优质号的近 12 月历史(易反爬,质量不稳)
- 新 SOP:**搜狗历史反扫废弃** — wewe-rss 订阅后自动持续 push,且包含订阅号的全量历史。Step 7 任务改为「识别新优质号 → 加入订阅 → wewe-rss 一次性补全历史」

### 7.1 优质号识别(三条线)

**线 1:从 Step 6.5 反链高频反推**
- 扫 `0_raw/commentaries/*.md` 的 `source_account` 字段,聚合每号:
  - 评论数(高频 push 信号)
  - 已关联政策评论占比(`related_policy != ~` / 总评论)
  - 平均 confidence
- 进入候选:评论数 ≥10 且关联占比 ≥30%

**线 2:从 Step 6 Tavily 兜底涌现**
- Step 6 Tavily pull 兜底时,如某 mp.weixin.qq.com 域反复命中(≥3 次/月) → 候选

**线 3:从 Step 7.5 引用反推(新增)**
- 已订阅优质号在 push 评论里**引用了某些公众号**(如「据 X 公众号分析」)
- 高频被引 ≥5 次/月 → 候选

### 7.2 候选评估(人工 + LLM)

对每个候选号做 light review:
- 翻 wewe-rss 订阅前查看 mp.weixin 公众号主页 / 搜索历史 5-10 篇标题样本
- LLM 一次过判定:观点独立性 / 政策相关性 / 商业广告占比 / 转发型占比
- 输出建议:`subscribe / observe / reject`

### 7.3 加入订阅(对 subscribe 候选)

- 在 wewe-rss 后台添加微信公众号订阅(需用户操作微信读书 App)
- 在 [[优质公众号白名单]] 加一行:号名 / 业务线 / 加入日期 / 加入理由
- 同步更新 `_meta/scripts/wewe_rss_to_commentaries.py:ACCOUNT_BUSINESS_MAP`(添加号→业务线映射)
- wewe-rss 订阅生效后**自动拉取该号全部可见历史**(替代旧 Step 7 搜狗翻页)

### 输出

- `_meta/scripts/log_step7_candidates_YYYYMMDD.json`(候选号 + 三线评分)
- 更新 [[优质公众号白名单]] + `wewe_rss_to_commentaries.py:ACCOUNT_BUSINESS_MAP`
- 反哺 Step 2 子线:新订阅号下次 cron 跑就开始 push

### 与原 SOP 的对照

| 项 | 旧 Step 7 | 新 Step 7 |
|---|---|---|
| 主工具 | 搜狗微信搜索翻页 + wechat-article-to-markdown | wewe-rss 订阅(被动 push) |
| 反爬风险 | 高(搜狗频控/验证码) | 0(本地 SQLite) |
| 历史覆盖 | 12 月手抓 | 订阅生效后自动全量 |
| 输出对象 | "优质源-历史引用清单" jsonl | 优质号订阅 + 业务标签映射(实际操作:wewe-rss UI + py 脚本 dict) |

**搜狗微信搜索路径完全废弃**,如需对未来接入 wewe-rss 不可达的公众号(私有/小号)可作为人工兜底,默认不走。

## Step 8 · 缺口分析 + 反哺渠道目录

**目的**:找出"漏了但圈内都在讨论"的政策,并修补采集源。

**动作**:
1. **对照**:Step 7 历史引用清单 vs Step 1 基线 + Step 5 新入库
2. **缺口分类**:
   - **Type A 政策遗漏**:政策存在但未收 → 直接回 Step 4 补抓
   - **Type B 渠道缺失**:政策来自渠道目录没有的源 → 新根域名加入 [[渠道目录]],标"下轮优先"
   - **Type C 地方政策盲区**:缺口集中在某省/市 → 省市级模板化批量补
3. **更新**:
   - `渠道目录.md` 追加新根域名,附首次发现日期与引入理由
   - `collection-meta/gaps-YYYYMMDD.jsonl` 记完整缺口清单
4. **反馈环**:Type B 新渠道下轮 Step 2 优先级最高;Type A 立即补抓不等下轮

**产出**:
- `gaps-YYYYMMDD.jsonl`
- 更新后的 `渠道目录.md`(frontmatter 加 `last_updated: YYYYMMDD`)

## 常见异常与应对

| 情况 | 应对 |
|------|------|
